# Netlify configuration: generated, not guessed

Every project Larpable creates must ship a `netlify.toml` at its root that matches the
project it deploys (PRD §8). This document records what the generator writes, why each
decision was made, and what the validator refuses to accept. The code is
`src/netlify/{facts,generator,validator,flow}.ts`; the tests are
`tests/netlify-*.test.ts` plus the gated `tests/guest/netlify.guest.test.ts`.

## The shape of the thing

```
inspectProjectFacts(environment)   → ProjectFacts   (facts.ts)
planNetlifyConfig(facts)           → NetlifyConfigPlan (generator.ts)
syncNetlifyConfig(environment, …)  → written | unchanged | preserved | blocked
validateNetlifyConfig({ toml, … }) → issues + verdict  (validator.ts)
ensureNetlifyConfig(environment, …)→ all of the above, in order  (flow.ts)
```

`ensureNetlifyConfig` is the only function an agent workflow needs to call. It inspects,
plans, writes, **reads the file back out of the environment**, and validates *that* file —
so a write that silently failed cannot be reported as success.

## What gets generated

For a Vite + React project on Bun whose guest reported Bun 1.4.5:

```toml
# netlify.toml — generated by Larpable from this project's own configuration.
#
# Framework: vite-react (`vite.config.ts` and on `react`.)
# Package manager: bun (`bun.lock` is the project's lockfile.)
#
# Edit the project, not this file: regenerate it and validate it again, so the
# configuration keeps matching what the project actually builds.

[build]
  command = "bun run build"
  publish = "dist"

[build.environment]
  BUN_VERSION = "1.4.5"

[[redirects]]
  from = "/*"
  to = "/index.html"
  status = 200
```

Four tables at most, and each one is conditional on a fact:

| Setting | When it appears | Where the value comes from |
| --- | --- | --- |
| `build.command` | the project has a `build` script or is a bundler project | `package.json` `scripts.build`, prefixed with the detected manager (`bun run`, `npm run`, `pnpm` per PRD §8.2) |
| `build.publish` | always | Vite `build.outDir`, then Astro `outDir`, then `react-scripts` → `build`, then `.` for static, then `dist` |
| `build.environment.BUN_VERSION` | the manager is Bun **and** the guest measured a version | the version the guest actually ran |
| `[functions]` | `netlify/functions/` holds at least one file | that directory |
| `[[redirects]]` | the build emits one HTML shell | `/*` → `/index.html`, status 200 |

Nothing else is written. PRD §8.6.6 asks to verify that no unnecessary deployment settings
were introduced, and the cheapest way to keep that true is not to emit them.

### Why the SPA fallback is conditional

PRD §8.4 says to add the fallback for client-side routing and *not* to add it to
applications that do not need it. The dividing line used here is what the build emits:

- **Astro** writes one HTML file per route. A catch-all would shadow them → no fallback.
- **Static HTML** is its own pages → no fallback.
- **Create React App** always renders one `index.html` → fallback.
- **Vite (React/Vue/Svelte/vanilla)** renders one `index.html` unless the root holds more
  than one HTML entry point → fallback for the single-page case, none for a multi-page one.
- **Unidentified projects** get no fallback. That is deliberate: an invented rewrite hides
  a misconfigured project, while a missing one is reported by the validator.

### Why Bun's version is pinned

PRD §8.2 says not to assume Bun is on Netlify's build image just because it works inside
unkernel. The generated file therefore pins `BUN_VERSION` to the version the guest actually
ran, which is the only version this project has been tested against. If the guest never
measured a version, no pin is written and the validator emits a warning saying so — an
invented number would be worse than an explicit gap.

## Keeping the file current

`syncNetlifyConfig` compares the plan with the file on disk and returns one of four
outcomes. The interesting ones are the middle two:

| Action | Meaning |
| --- | --- |
| `written` | no file, an unparseable file, or a file whose only settings are ones Larpable owns and which no longer match |
| `unchanged` | the settings already match, **so the bytes are left alone** — hand formatting, key order and comments survive |
| `preserved` | the file contains settings Larpable does not manage (`[[headers]]`, `[context.*]`, plugins, `build.base`, application redirects), so nothing is written |
| `blocked` | the project cannot justify a configuration (unknown framework, no build script), so nothing is written |

"Preserved" is not "approved": a preserved file is still validated, and a hand-written file
without an SPA fallback comes back as *not ready* with the specific issue. The alternative —
rewriting every file that does not match the plan — would delete a user's headers on the
first sync, which is a worse failure than a reported warning.

## What the validator checks

Each check answers with an issue code, a sentence and a hint, because "invalid" alone gives
an agent nothing to fix.

| Code | Severity | Check |
| --- | --- | --- |
| `missing-file` | error | `netlify.toml` exists |
| `not-at-root` | error | it is at the project root, where Netlify reads it |
| `invalid-toml` | error | the file parses as TOML (real parser, not a regex) |
| `missing-command` / `command-mismatch` | error | `build.command` equals the manager + `scripts.build` |
| `unnecessary-command` | warning | no command on a project with nothing to build |
| `missing-publish` / `publish-mismatch` | error | `publish` matches the project's own configuration |
| `publish-vs-build` | error | `publish` matches the directory the last build **actually wrote** |
| `missing-entry` / `empty-publish` | error | that directory has a readable `index.html` and is not empty |
| `missing-spa-redirect` | error | an SPA has its fallback |
| `unneeded-spa-redirect` | warning | a non-SPA does not |
| `shadowed-redirect` | error | the catch-all is last, so no rule after it is dead |
| `duplicate-spa-redirect` | error | at most one `/*` rule |
| `invalid-redirect-status` / `invalid-redirect-target` | error | status is one Netlify accepts; `from`/`to` are non-empty; an SPA fallback is a 200 to `/index.html` |
| `forced-catch-all` | warning | `force = true` on `/*` would shadow real assets |
| `missing-functions` / `unnecessary-functions` | error / warning | the configured functions directory is the one that exists, and only when it exists |
| `bun-version-unpinned` / `unnecessary-bun-version` | warning | `BUN_VERSION` is pinned exactly when the project uses Bun |
| `unnecessary-base` | warning | `build.base` is not the default `.` |

Warnings keep `ok: true`; errors do not. A validation that has not seen a build says so in
its summary ("the publish check ran against the project's configuration") rather than
implying a build was checked.

## Known limits

- **Yarn.** A project whose only lockfile is `yarn.lock` is configured with npm and told
  about it. Larpable generates npm/Bun/pnpm commands only; silently emitting `yarn` would
  contradict the manager it verified the build with.
- **Netlify's build image.** The generated file is checked against *this* project's facts.
  Whether a given `BUN_VERSION` exists in Netlify's image is Netlify's catalogue, not
  something the guest can observe; the pin makes the assumption explicit and changeable in
  one place.
- **Functions.** Only the directory is configured. Whether a function actually works is a
  deployment-time question that the browser-hosted guest cannot answer (PRD §8.5).
- **Deployment itself.** `netlify deploy` is out of scope (PRD §8.7); Larpable produces the
  file, not the upload.
