# Spacing audit — where the pixels were, and what was tightened

Generated by `bun run evidence:spacing` (`scripts/spacing-evidence.ts`), which loads the real app
in Chromium at 390 x 844 and 1440 x 900, opens the two popovers, and writes each layout box's
computed padding, margin, gap and rectangle to `spacing-<label>.{json,txt}` plus a screenshot per
viewport. Nothing here is a claim about what the CSS should do: every number was read out of the
live page with `getComputedStyle` and `getBoundingClientRect`.

The two runs are comparable: `--label=before` was taken with the pre-change sources (only the
`data-testid="app-shell"` hook re-added, which is an attribute, not a spacing rule), `--label=after`
with the tightened ones. Any non-`before` label re-prints the deltas automatically when
`spacing-before.json` is present — that is the "before → after" block at the foot of
`spacing-after.txt`.

## The measurement that decided the work

The shell was already tight. Before any change, every surface came in at or under 8 px on the
sides — the transcript and prompt box at 8/6 px, the terminal tab strip at 6 px, the debug popover
at 8 px. The generous boxes were the exceptions, and they were exceptions in *both* directions:

- `header` — 10 px per side at 1440 while the same header uses 6 px at 390, and while every pane
  under it uses 6–8 px.
- `#preview-heading` — 8 px at 390, **16 px at 1440**: the widest gutter in the app, on the caption
  of the column whose content sits at 6 px.
- The popover's handset-note rows — `p-2` (8 px) among neighbours at 6 px.

## Before → after (px, top/right/bottom/left)

| surface | 390 x 844 | 1440 x 900 |
| --- | --- | --- |
| `header` | 5.6/6/4/6 → unchanged | 4/**10**/4/**10** → 4/**8**/4/**8** |
| `chat-transcript` | 4/**8**/4/**8** → 4/**6**/4/**6** | 4/**8**/4/**8** → 4/**6**/4/**6** |
| `#preview-heading` | 2/8/2/8 → 2/6/2/6 (hidden at this width) | 2/**16**/2/**16** → 2/**8**/2/**8** |
| `page overflow` | 0 → 0 px | 0 → 0 px |

No other measured box moved: the shell, panes, tab strips, browser bar, debug popover and settings
panel report the same numbers in both runs. The popover is still 352 x 416 at both viewports, so
the densest surface did not reflow.

## The other four tightenings, and how they are held

These sit inside the surfaces above, so the geometry numbers cannot show them; each is held by
either the browser audit or a test rather than by a screenshot.

| file:line | change | held by |
| --- | --- | --- |
| `src/ui/chat-panel.tsx` transcript | `px-2 space-y-1.5` → `px-1.5 space-y-1` | this audit (`chat-transcript` padding) |
| `src/ui/dashboard.tsx` preview caption | `px-2 sm:px-4` → `px-1.5 sm:px-2` | this audit (`preview-heading` padding) |
| `src/ui/dashboard.tsx` empty agent pane | `px-2 py-2` → `px-1.5 py-1.5` | matched to `preview-frame.tsx`'s twin |
| `src/ui/preview-frame.tsx` empty preview | `px-2 py-2` → `px-1.5 py-1.5` | matched to the chat placeholder |
| `src/ui/terminal-panel.tsx` empty shell | `px-3` → `px-2` | matched to the terminal tab strip |
| `src/ui/preview-chrome.tsx` viewport hint | `gap-3` → `gap-2` | `justify-between`, so the gap is only a floor |
| `src/ui/environment-panel.tsx` note row | `gap-2 p-2` → `gap-1.5 p-1.5` | `tests/mobile-layout.test.tsx` (phone-only rows) |

The note rows only render for a handset, so the desktop audit cannot see them; the test renders
`EnvironmentPanel` with iPhone facts and asserts the tightened class list. It was proven to
discriminate by putting `p-2` back: the test failed, and passed again once reverted.

## What was deliberately not touched

- **Touch targets.** Every icon button keeps `TOUCH_TARGET_ICON` (36 px box + 4 px margin = 44 px
  hit area) and the stage tabs keep `max-lg:min-h-11`; `tests/mobile-layout.test.tsx` still pins
  both. The audit's "smallest control 36 px" line is unchanged before and after.
- **Safe-area insets.** `pt-[max(0.35rem,var(--safe-top))]` on the header and
  `pb-[max(0.35rem,var(--safe-bottom))]` on the shell are untouched: they are the insets that keep
  the app off a notch and a home indicator, not decoration.
- **The inner components.** `IconButton`/`Button` already sit at `px-1.5 py-0.5`–`px-2`, so the
  tightening was about the boxes *around* them; shrinking the controls themselves would have
  bought 2 px each and cost the touch floor.

## Two pre-existing reds seen while measuring (not caused by this change)

`bun run acceptance:mobile` reports 12 passed / 2 failed on this branch, and reports the same two
with the pre-change sources stashed: the touch-floor check fails at both viewports because five
controls ("Send the prompt", "Copy the selection", "Paste from the clipboard", "Cut …", "Clear the
terminal") are "covered at its centre by DIV" — an `elementFromPoint` hit test finding a DIV over
the button — and the live pass cannot click `boot-button` because it is still disabled ("Booting…")
after 30 s. Neither depends on any class in the table above; both are recorded as their own goals.
